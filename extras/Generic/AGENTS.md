## 基本准则

- 当识别到用户指令存在瑕疵或错误时，先分析并指出问题所在，给出修正思路与改进版本，说明更正理由，得到确认再执行
- 遇到任务被系统阻止时，说明受阻的操作和原因；若该操作有必要，直接输出可执行指令，让用户执行
- Windows 的路径优先用正斜杠（/），遇到异常再试反斜杠
- 禁止删除 git 仓库外的文件，给出项目清单，把命令给用户执行
- 依赖与包管理统一使用 `uv` 和 `pnpm`，不要使用 `npm` 和 `pip`
- 查询 GitHub 优先用 `gh` 工具
- 下载 GitHub Release 或 Raw 文件时，在原始完整 URL 前加 `https://gh-proxy.org/` 使用代理
- 拉取 Docker 镜像时使用用户 ~/.dotfiles/pwsh 中的 docker-pull-mirror 函数
- 能确定版本号时优先从源码而不是逆向分析，shallow clone 到临时路径

## 代码编写

- 按照以下顺序完成编码流程，无需逐步确认：首先实现满足需求的最简可行版本；然后评估更优方案，只采纳有实际收益的改进；接着消除冗余、简化结构和不必要的抽象，同时保持功能正确和代码清晰；最后在关键设计或难以理解的逻辑处添加必要注释。代码应当简单、易读、符合语言习惯，避免过度设计。默认不添加异常处理、防御性检查或回退逻辑，除非用户明确要求，或者确实需要这些机制来保证正确性和安全性
- 不为罕见竞态或边界情况加复杂度；确需处理时先说明具体怎么出错、概率多大、要多写多少代码，同意后再做。不擅自扩大改动范围
- 外部输入只在入口校验一次，内部按已确定的类型传递，不重复做防御性检查
- 不提前抽只用一次的函数；主函数只写正常流程，校验和细节下沉到小函数；注释只写不明显的约束和反直觉行为
- 自动生成的文件改源头后重新生成，不手改；测试测真实实现，不把业务逻辑抄进测试，尽量少用 mock
- 除非用户指明，否则修改还未提交的代码时不要保留兼容性的代码、文档、说明，不要为已不存在的逻辑留下注释
- 完成后无需自测，不用提自测
- When building user interfaces, avoid unnecessary secondary labels and descriptions. Let the layout do the explaining.

## 给 Codex 看

- PowerShell 优先使用 `login: false`，需要 profile 时再加载。
- 独立任务优先委派子代理，主代理同时推进其他不重叠的工作，避免空等、重复工作和修改冲突。根据任务的推理难度、影响范围和风险选择模型：文件定位、代码检索、信息提取和格式调整等简单任务使用 Luna；功能开发、常规 Bug 修复、测试编写和代码审查等普通任务使用 Terra；架构设计、跨模块重构、疑难排查和复杂逻辑推理等复杂任务使用 Sol。子代理的模型等级不得高于主代理，超出时降至主代理同级，用户明确指定的除外。

## Git 提交与推送

- 根代理直接委派 Git 提交和推送；子代理自己完成任务，不再委派。
- 状态检查、`git diff`、差异分析、提交信息生成和结果核对均由执行代理独立完成；主代理不预先执行或重复这些操作。
- T3 Code 中，先用 `orchestrator_capabilities` 查找 Claude Code provider 的 MiniMax 系列模型，再通过 `delegate_task` 委派；其他环境使用原生 `git-commit` Agent。指定 provider/model 不可用时报告受阻，不自行替换。
- 委派任务一次给齐仓库绝对路径、提交范围、根代理自己的模型名称、用户提供的提交信息、当前会话总结及是否允许推送。执行代理负责完整流程。
